# PROMPT FOR AI: CREATE REVISO CAPSTONE PRESENTATION GUIDES

## Context
I have a capstone project called **Reviso** — an AI-enhanced board exam preparation system for Pasig Catholic College. I have project documentation including architecture diagrams, requirements specifications, and FDD diagrams. I need to present this to a capstone panel.

## What I Need
Create presentation guides that help me **explain (not read)** my project to academic panelists. The guides should focus on HOW to deliver the content, not scripts or bullet points.

## Key Documents You'll Find in My Project
1. **Architecture Diagram** — System modules and data flows
2. **Functional Decomposition Diagram (FDD)** — Hierarchical breakdown of system functions
3. **Analysis & Design Phase Documentation** — Current problems, requirements, specifications
4. **Hardware/Infrastructure specs** — Server setup and deployment model
5. **Functional Requirements** — What the system must do (centralize materials, AI exam creation, analytics, controlled access)
6. **Non-Functional Requirements** — Quality standards (scalability, security, reliability, usability)

## What I Mean By "Explain, Not Read"
- Don't create scripts or bullet-point lists I'll just read aloud
- Create **frameworks** and **narrative structures** that show me HOW to contextualize each concept
- Show me how to transition between topics naturally
- Help me see **connections** between requirements and design (e.g., how FDD implements functional requirements)
- Teach me how to answer likely panelist questions

## Presentation Structure (What I'll Be Covering)
1. **Architecture Overview** — System design and modules
2. **Functional Requirements** — What Reviso must do (organize around problems, not feature lists)
3. **Non-Functional Requirements** — How well it must work (quality standards)
4. **FDD Deep-Dive** — Show the hierarchical breakdown and explain each module
5. **Hardware & Infrastructure** — Deployment and scalability

## Tone & Language
- **Academic but accessible** — Panelists are professors, not software engineers
- **Problem-first** — Start with "what pain point does this solve?" before naming features
- **Story-based** — Show how a student/teacher would use the system, don't just list features
- **No jargon without context** — If you use technical terms, briefly explain why they matter

## Deliverables I Need
1. **Comprehensive Guide** (~3000+ words)
   - For each section of my presentation, explain:
     - What panelists want to know
     - How to contextualize the concept
     - How to transition to related topics
     - How to handle common questions
   - Include examples of good vs bad explanations

2. **Quick Reference Cheat Sheet** (~1500 words)
   - Condensed talking points (1-3 sentences each)
   - Timing guidance
   - Delivery tips specific to academic presentations
   - Common panelist questions + answer templates

3. **Visual Explanation Guide**
   - For FDD: Show how to walk through the diagram step-by-step
   - For each module: Explain what functions it contains and why
   - For requirements: Show how to map functional requirements to FDD modules

## Important Constraints
- **Don't assume I'm a presentation expert** — Give practical delivery advice
- **Don't create PowerPoint content** — I have my own slides; help me present them better
- **Don't oversimplify** — Panelists are academics; they appreciate nuance
- **Don't invent details** — Stick to what's in my project documentation; if something is unclear, ask for clarification instead of making it up

## Question-Handling Guidance
For each major topic, include:
- 2-3 questions panelists are likely to ask
- Why they'd ask (what concern are they expressing?)
- How to answer confidently without being defensive

## Format
- Markdown files (easy to read, print, annotate)
- Clear section headings and subsections
- Use tables or comparison frameworks where helpful
- Include example dialogues ("What you might say" vs "What to avoid")

## Example of What I'm Looking For

**BAD GUIDE:**
> "Functional requirements include: centralize materials, AI-assisted exam creation, performance analytics, and controlled access."

**GOOD GUIDE:**
> "Don't list requirements. Instead, say: 'Right now at Pasig Catholic College, teachers spend 2-4 hours writing exams manually. Students have no feedback beyond a score. Our functional requirements solve these problems. First, centralize materials so students don't hunt through 5 drives. Second, AI-assisted exam creation so teachers save 3+ hours. Third, performance analytics so students get real feedback. Fourth, controlled access so exam integrity is maintained. Each requirement solves a specific pain point.'
>
> This grounds abstract requirements in real problems panelists care about."
